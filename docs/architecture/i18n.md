# Internationalization

Last verified: 2026-09-16 against commit c0fde76.

Two unrelated i18n systems coexist: one for UI chrome (labels, buttons, headings — translated by editing files in the repo and deploying) and one for editorial content (lexicon entries, page bodies — translated by editors typing into Filament and stored in the database). They use different locale sets, different storage, and different mechanisms for choosing which language a visitor sees, and neither system is aware of the other.

## System 1: UI strings

Laravel's standard JSON translation files, one per locale, at `server/resources/lang/{en,es,te}.json`, plus a handful of untouched Laravel-stub PHP files at `server/resources/lang/en/{auth,pagination,passwords,validation}.php` (English only — no `es`/`te` equivalents exist for these, so validation and auth-flow error messages always render in English regardless of viewer locale).

Keys are namespaced by dot-separated section, documented in `server/resources/lang/README_translations.txt` (the only project-authored doc that existed before this one): `lexicon.general.*` for text shared across lexicon pages, `lexicon.pages.(page_name).*` for page-specific text (page names should track their URL segment), `lexicon.pages.(page_name).html_head_title` / `.page_title` for `<title>` and `<h1>` text, and `lexicon.header` / `lexicon.menu` / `lexicon.sidebar` for chrome shared across most pages. Placeholders (`:name`) and pipe-delimited pluralization (`"1 word|:count words"`) follow ordinary Laravel conventions.

One key deserves special mention: `lexicon.pages.data.column_header_<Display Name>`. The Data page looks up a column header translation by **appending the column's literal display name** (from `LexLexicon::getDataColumns()`, see `docs/architecture/data-cache.md`) to this prefix — so a column named `Deptotic` needs a translation key spelled exactly `lexicon.pages.data.column_header_Deptotic` in all three JSON files, spaces and capitalization included. Add a new lexicon column and you must add a matching key to `en.json`, `es.json`, and `te.json` or the header falls back to Laravel's raw-key rendering.

`lexicon.pages.data.datatables_translation_file` names a DataTables i18n JSON file to load for the Data page's own generated UI text (search box, pagination, "showing X of Y", empty-state message — everything DataTables itself renders, distinct from the site's own translation keys). Current values:

| Locale | Value | File |
|---|---|---|
| `en` | `en-US.json` | none needed — `lex_data.blade.php` skips loading a file when the value is exactly `"en-US.json"`, relying on DataTables' English default |
| `es` | `es-MX.json` | `server/public/assets/datatables/plugins/i18n/es-MX.json` |
| `te` | `te.json` | `server/public/assets/datatables/plugins/i18n/te.json`, downloaded 2026-08-15 from the DataTables CDN; covers only DataTables' core UI strings — any key it omits falls back to English |

## System 2: content translation (spatie/laravel-translatable)

Models that hold editorial content use `Spatie\Translatable\HasTranslations` with a `$translatable` array naming which attributes are stored as `{"en": "...", "es": "...", "te": "..."}` JSON rather than plain strings. Confirmed via `grep -rl HasTranslations app/Models/`:

`LexLanguageSubFamily`, `LexLanguage`, `LexReflexCrossReference`, `LexPartOfSpeech`, `Page`, `LexSemanticField`, `LexLanguageFamily`, `LexLexicon` (`protolang_name`, `protolanguage_page_content`, `landing_page_content`), `LexReflexExtraData`, `LexSemanticCategory`, `LexEtyma`, `LexEtymaExtraData`, `LexReflex`.

Filament edits these through the `lara-zeus/spatie-translatable` package (`LaraZeus\SpatieTranslatable\SpatieTranslatablePlugin`), configured in `app/Providers/Filament/AdminPanelProvider.php`:

```php
->plugin(SpatieTranslatablePlugin::make()->defaultLocales(['en', 'es', 'te'])->useFallbackLocale())
```

This is the one place the set of editable content locales is declared for the admin. A locale-switcher control appears in the top-right of any translatable form field in Filament.

## Which locale a visitor sees

The public site's "viewer language" is unrelated to the browser's `Accept-Language` header or to Laravel's app locale by default — it is chosen per-lexicon and stored in the session:

1. Each `LexLexicon` row has a `viewer_lang_options` string column (free text, comma-separated, e.g. `"en, es"`), edited via a plain `TextInput` in `LexLexiconForm.php` with no validation against the actual `en`/`es`/`te` set.
2. `LexLexicon::getViewerLangsArray()` splits that string into an array; the language switcher in `resources/views/lexicon/layout.blade.php:224-231` renders one link per option, each pointing at `GET /lexicon/{slug}/switchlang/{lang}?return_to=<current-url>`.
3. `PublicLexiconController::switch_lang()` does `Session::put('viewer_lang_code', $lang)`, then redirects the reader back to the page they came from, or to the lexicon home.
4. `App\Http\Middleware\SetLocaleFromSessionMiddleware`, registered in the `web` middleware group in `app/Http/Kernel.php`, runs on every request and calls `App::setLocale(Session::get('viewer_lang_code'))` whenever the session has that key — this is what makes both System 1 lookups (`__()`/`Lang::get()`) and System 2 attribute access (`$model->translatable_attr`, which spatie resolves against the current app locale) follow the visitor's chosen viewer language.
5. `PublicLexiconController::ajaxData()` separately reads `Session::get('viewer_lang_code', 'en')` to pick which `content_lang_code` slice of `lex_lexicon_data_cache` to query — so the Data page's cache rows must exist for a locale before it's usable there, independent of step 4.
6. Display names for the switcher itself (`"English"`, `"Español"`, `"తెలుగు"`) come from a small hard-coded map in `LexLexicon::getDisplayTextViewerLang()` (`server/app/Models/LexLexicon.php:47-51`) — a fourth place a new locale must be added, and it returns `"Unknown: <code>"` for anything not in the map.

Because the choice lives only in the session, a shared link to a Spanish-language view opens in whatever locale the recipient's session already holds (usually English), and there is no `hreflang` markup anywhere in the lexicon layouts.

## Adding a viewer language: every place that must change

See `docs/runbooks/adding-a-viewer-language.md` for the ordered checklist. In summary, precisely these locations encode the current locale set and must all be updated together:

1. `server/resources/lang/<code>.json` — a full copy of the UI strings, including every `column_header_*` key already in use by any lexicon.
2. `LaraZeus\SpatieTranslatablePlugin::make()->defaultLocales([...])` in `app/Providers/Filament/AdminPanelProvider.php` — otherwise Filament never offers the locale as an editable tab on translatable fields.
3. `LexLexicon::getDisplayTextViewerLang()` in `app/Models/LexLexicon.php` — the display-name map for the language switcher.
4. Each lexicon's `viewer_lang_options` column (edited per-lexicon in Filament, or via `LexLexicon::where(...)->update(['viewer_lang_options' => ...])`) — a language isn't offered to visitors of a given lexicon until this is updated for that lexicon.
5. `app:generate-lexicon-data-cache <lexicon_id>` re-run for every lexicon that added the locale — `GenerateLexiconDataCache` only writes cache rows for locales listed in `viewer_lang_options` at the time it runs.
6. A DataTables i18n file at `server/public/assets/datatables/plugins/i18n/<file>.json` (download from the DataTables CDN or the `DataTables/Plugins` GitHub repo) plus a matching `lexicon.pages.data.datatables_translation_file` value in the new `<code>.json`.
7. `server/resources/lang/en/{auth,validation,pagination,passwords}.php` if the new locale should also localize Laravel's built-in auth/validation messages — currently only `en` exists for these, so this step has never actually been done for `es` or `te` either.
