# Local development

Last verified: 2026-09-16 against commit c0fde76.

This is the step-by-step procedure for getting the LRC platform running on a developer machine, using only Docker — no PHP, Composer, or Node install on the host is assumed or required.

## Prerequisites

- Docker Desktop (or an equivalent Docker Engine + Compose v2 install). Everything else runs in containers.
- Node/npm on the host is optional — only useful if you'd rather run `npm`/`vite` outside a container for faster asset rebuilds. `make npm ARGS="..."` runs it in a container either way.
- This repo cloned, with `server/` present (it is bind-mounted into the `web` container by `compose.yaml`, so edits to `server/` on the host are picked up immediately — no image rebuild needed for PHP/Blade changes).

## First run

1. `make init` — first-time setup. Creates `compose.override.yaml` from `compose.override.yaml.example` with a freshly generated `APP_KEY` (via `openssl rand -base64 32`, substituted for the example's `APP_KEY=base64:REPLACE_ME` placeholder — see "`compose.override.yaml` and `APP_KEY`" below), installs Composer and npm dependencies in throwaway containers (not the `web` image itself, so dev dependencies needed for tests exist under the bind mount even though the image is built with `--no-dev`), and builds the `web` image.
2. `make up` — starts the `web` and `db` services in the background and prints the local URL (it runs `docker compose port web 80` for you).
   - Raw equivalent: `docker compose up -d && docker compose port web 80`.
3. Wait a few seconds for MariaDB to finish initializing on first boot (`docker compose logs -f db` until you see it accepting connections), then run migrations:
   - `make artisan ARGS="migrate"`
   - Raw equivalent: `docker compose exec web php artisan migrate`
   - This also seeds the Spatie `roles`/`permissions` tables, because — despite `database/seeders/DatabaseSeeder.php` being empty — the roles and role-permission assignments (`Site Manager`, `EIEOL Manager`, `Lexicon Manager` and their permissions) are created by a migration (`database/migrations/2022_03_21_102536_add_initial_roles_permissions.php`), not a seeder. A fresh `migrate` gives you working roles with no user assigned to any of them yet.
4. Load a database dump if you have one — see `docs/runbooks/loading-a-database-dump.md`. Without a dump, the lexicon and EIEOL tables are simply empty after step 3.
5. Build front-end assets: `make build` for a one-off production-style Vite build, or `make dev` to run Vite's dev server in the foreground with hot reload (publishes port 5173; leave it running in a separate terminal). Both run in a throwaway Node container against the bind-mounted `server/`, not inside the `web` container. `make npm ARGS="..."` is available for any other npm/Vite invocation.
6. Create a first admin user and grant it a role — see `docs/runbooks/loading-a-database-dump.md` for the exact tinker commands and permission names, since this is normally done once, right after loading (or in place of) a dump.

## Reaching the site: the proxy assumption

`compose.yaml` sets `VIRTUAL_HOST=lrc.localhost.utexas.edu` and `APP_URL=https://lrc.localhost.utexas.edu` on the `web` service, and publishes container port 80 with no fixed host port (`ports: - "80"`). Those `VIRTUAL_HOST`/`APP_URL` values are meant for an external reverse proxy (a `jwilder/nginx-proxy`-style container watching `VIRTUAL_HOST` labels, or a shared LAITS dev-machine proxy) that is **not** started by `compose.yaml` itself — there is no such proxy service in this repo.

**Without that proxy** (the common case on a personal dev machine):
1. Find the host port Docker assigned to container port 80: `docker compose port web 80` (also printed automatically by `make up`; the value is `0.0.0.0:<port>`). Uncomment the `ports: - "8080:80"` line in `compose.override.yaml` if you'd rather pin a fixed host port instead of a random one.
2. Browse to `http://localhost:<port>/admin` directly. Laravel's own routing doesn't care what `Host` header arrives as long as you don't hit code that hard-checks `APP_URL` (asset URLs generated by `asset()`/`Vite::asset()` do use `APP_URL`, so some CSS/JS references may point at `https://lrc.localhost.utexas.edu` instead of your real host — if assets 404, override `APP_URL` in `compose.override.yaml` to match the port from step 1).

## `compose.override.yaml` and `APP_KEY`

`compose.yaml` is committed and no longer carries a real `APP_KEY` — it only comments that the key lives in `compose.override.yaml`, created by `make init` from `compose.override.yaml.example`. `compose.override.yaml` is gitignored (`.gitignore`: `/compose.override.yaml`) and is where `make init` places your own copy, with `APP_KEY=base64:REPLACE_ME` already substituted for a freshly generated key (`openssl rand -base64 32`). Use the same file to override `DB_*` ports, `VIRTUAL_HOST`, or `APP_URL` per developer/machine without committing secrets — Compose automatically merges `compose.override.yaml` over `compose.yaml`.

`make init` only writes `compose.override.yaml` if it doesn't already exist, so re-running `make init` won't clobber a key you're already using. To generate a different key yourself: `openssl rand -base64 32`, prefix the output with `base64:`, and paste it into `compose.override.yaml`'s `APP_KEY` line.

## Running migrations

`make artisan ARGS="migrate"` (raw: `docker compose exec web php artisan migrate`). Re-run after pulling any change that adds a migration file. There is no `migrate:fresh` shortcut documented here deliberately — running it against a dump you care about will drop everything; use it only on a disposable database.

## Running tests

```
make test
```
(raw: `docker compose exec -u www-data -e DB_DATABASE=lrc_test web php artisan test`)

Tests run against a separate `lrc_test` database inside the `db` container, which `make test` creates and grants on first use. They never touch the `lrc` development database, so `RefreshDatabase` in a test is safe. Filter with `make test ARGS="--filter SomeTest"`.

## Logging in to `/admin`

Filament's login lives at `/admin/login` (a second, legacy auth stack also exists at `/login` via `laravel/ui`, unrelated to Filament — see the platform review §3). Use the email/password you created in `docs/runbooks/loading-a-database-dump.md`.

## Common problems

| Symptom | Cause | Fix |
|---|---|---|
| 500 error, log mentions `storage/framework/...` or `bootstrap/cache/...` not writable | The image sets `chmod 777 -R` on those directories at build time (`Dockerfile`), but a bind-mounted `server/` from certain hosts (or a volume recreated after an `npm`/`composer` run as a different UID) can end up with directory permissions the `www-data`/container user can't write to | `docker compose exec web chmod -R 777 storage bootstrap/cache` |
| Changes to `server/` PHP/Blade files don't appear | You edited a copy that isn't actually bind-mounted, or you're hitting a stale `view:cache`/`config:cache` from a previous production-style build | Confirm `docker compose config` shows `./server:/var/www/html` under `web.volumes`; run `docker compose exec web php artisan view:clear config:clear` |
| Cache settings seem ignored | `config/cache.php` reads `CACHE_STORE`; older setups used `CACHE_DRIVER`. `compose.yaml` and `.env.example` now use `CACHE_STORE`. If you carry an old `compose.override.yaml` or `.env`, rename the variable. |
| Assets 404 or point at the wrong host | `APP_URL` mismatch between the committed `lrc.localhost.utexas.edu` value and whatever host/port you're actually browsing to | Override `APP_URL` in `compose.override.yaml` to match, then `php artisan config:clear` |
| `make dev` assets don't hot-reload in the browser | `make dev` publishes port 5173 from its own throwaway container; depending on your Docker networking mode the host browser may not reach it directly, or another process already holds 5173 | Prefer `make build` for a one-off check, or confirm port 5173 is free and reachable per your Docker setup |
- **`make init` hangs at "Unable to find image ... locally".** Docker cannot reach Docker Hub. Check Docker Desktop → Settings → Resources → Proxies (UT networks and VPNs sometimes require one), or try another network. `docker pull hello-world` is the quickest test. Nothing in this repository can be built until pulls work.
- **Every page returns 500 with `tempnam(): file created in the system's temporary directory`.** Apache runs PHP as `www-data`; if artisan was run as root (plain `docker compose exec web php artisan ...`), root now owns the compiled-view directory `/tmp/laravel` or files under `storage/`. Always use the `make` targets, which run as `www-data`; `make up` also fixes the ownership of `/tmp/laravel`. To repair by hand: `docker compose exec web chown -R www-data /tmp/laravel storage bootstrap/cache`.

## Verify

- `docker compose ps` shows `web` and `db` both `Up`.
- `curl -I http://localhost:<port>/` (from `docker compose port web 80`) returns a `200` or `30x`, not a connection refused.
- `/admin/login` loads and accepts the admin credentials created per `docs/runbooks/loading-a-database-dump.md`.
- `make test` (or the raw `php artisan test`) runs the stub test suite without a database-connection error.
